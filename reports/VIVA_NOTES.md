## As-of history and the concurrency leak

**What it is.** A rule that a CI run may only use results of runs that had *finished* when it started.

**How it works.** Each run gets start = build_timestamp and end = start + build_duration (capped at 24 h). Run Q informs run R iff Q.end ≤ R.start. The store applies runs to per-test state in end order while visiting runs in start order.

**Why we chose it here.** LRTS computes 'last outcome' from the previous run *by start time*. CI runs overlap, so that previous run had often not finished: using its outcome is information from the future.

**Our result and what it means.** Previous run unfinished at start: 49.8% macro (Kafka 77.8%); 45.8% of 'last outcome = fail' values come from unfinished runs. Brute-force check: 50/50 random runs recomputed from raw tables match the store.

**Likely questions.**
- *Why cap durations at 24 h?* p99.9 of build_duration is 25.6 h and 0.12% of runs exceed 24 h; values up to 83 days are not test time. Capping makes those runs visible earlier, a deliberate, tiny relaxation.
- *Does the leak inflate the paper's numbers?* See BASELINES.md §3: same features, same runs, start order vs as-of.

## Negative sampling and recalibration

**What it is.** Training on all positives and only a sample of negatives, with weights, then re-mapping probabilities.

**How it works.** Per training run: all failing rows; up to K = 200 passing rows, half from tests related to the change. Each sampled row is weighted by stratum size / sample size. Probabilities are then calibrated by isotonic regression on unsampled validation rows (valB).

**Why we chose it here.** 104M rows with ~0.24% positives do not fit in 2 GB RAM and are dominated by easy negatives.

**Our result and what it means.** Training rows: 1,527,243 for Kafka (see train_sample.json for all). Brier before/after calibration: MODELING.md §calibration.

**Likely questions.**
- *Why calibrate at all if ranking is what matters?* The ordering rule divides P by duration; a mis-scaled P changes the trade-off between risk and cost.
- *Why isotonic, not Platt?* Isotonic is monotone and non-parametric; with millions of validation rows it does not overfit, and Platt (reported too) assumes a sigmoid shape.

## PR-AUC vs accuracy and ROC-AUC

**What it is.** Precision-recall area: average precision over recall levels.

**How it works.** Sort rows by score; precision at each positive, averaged.

**Why we chose it here.** Base rate is 0.2428%: always predicting 'pass' is 99.76% accurate and useless. ROC-AUC rewards ranking the huge negative mass correctly and looks optimistic; PR-AUC focuses on the few positives.

**Our result and what it means.** MODELING.md: PR-AUC (primary), ROC-AUC alongside.

**Likely questions.**
- *Why is ROC-AUC high but PR-AUC low?* With 400 negatives per positive, a small false-positive *rate* is still many false positives, which ROC hides and PR shows.

## L1 vs L2 regularisation

**What it is.** Penalties on coefficient size in logistic regression: L1 = sum |w|, L2 = sum w².

**How it works.** The loss adds λ·penalty; C = 1/λ. L1's corner at 0 sets weak coefficients exactly to zero (feature selection); L2 shrinks all smoothly and handles correlated features by sharing weight.

**Why we chose it here.** Many correlated history features (h_ and hs_ counts, fail rate) and drift over time: a penalty limits variance and reveals which features carry independent signal.

**Our result and what it means.** Best LR: elasticnet with C = 0.0001 (valA PR-AUC 0.163). Coefficients set to zero by L1: figure reg_lr_l1_path.png.

**Likely questions.**
- *Why standardise first?* Penalties compare coefficient sizes; without a common scale the penalty would depend on units.

## Early stopping and tree constraints (LightGBM, random forest)

**What it is.** Stopping boosting when validation loss stops improving; limiting tree size.

**How it works.** LightGBM: num_leaves, max_depth, min_child_samples, L1/L2 on leaf values, feature/bagging fractions, learning rate; training stops after 100 rounds without valA PR-AUC gain. RF: max_depth, min_samples_leaf, max_features.

**Why we chose it here.** Extreme imbalance means trees can carve out tiny leaves around a few positives (memorising); constraints and early stopping trade a little training fit for out-of-time generalisation.

**Our result and what it means.** Refit stopped at 432 rounds; regularised vs unregularised curves: reg_lgbm_curves.png; RF train/val gap vs depth: reg_rf_depth.png.

**Likely questions.**
- *Why not tune on the test split?* Then the reported number would be optimistic by the amount of selection; test is touched once.

## Bagging vs boosting

**What it is.** Bagging: average many trees fitted on bootstrap samples (random forest). Boosting: add trees sequentially, each fitting the errors of the ensemble so far (LightGBM).

**How it works.** Bagging reduces variance; boosting reduces bias and needs regularisation to avoid overfitting.

**Why we chose it here.** Both are standard for tabular data; comparing them on the same features shows whether the signal is mostly variance-limited (bagging helps) or bias-limited (boosting helps).

**Our result and what it means.** MODELING.md compares PR-AUC and APFDc on the same test runs.

**Likely questions.**
- *Why is LightGBM usually better here?* Rare positives and interactions (e.g. recent failure × related path) are learned incrementally; RF's averaged deep trees are less sharp on the extreme tail.

## Soft voting and stacking

**What it is.** Soft voting: average calibrated probabilities of LR, RF and LightGBM. Stacking: a logistic regression that learns how to combine them.

**How it works.** Stacker inputs on valB: the three base logits, the cbt_LastFail rank within the run and the ChangedOrNewFirst indicator.

**Why we chose it here.** Ensembles help when base models make *different* errors; the residual-correlation matrix shows whether they do.

**Our result and what it means.** MODELING.md §ensembles and the error-correlation matrix.

**Likely questions.**
- *Why can an ensemble fail to help?* If the members' errors are highly correlated, averaging removes little error and adds the weaker models' noise.

## Optuna / TPE

**What it is.** Bayesian hyperparameter search with a Tree-structured Parzen Estimator.

**How it works.** TPE models the density of good and bad configurations and proposes points with a high ratio; a median pruner stops trials whose intermediate PR-AUC lags.

**Why we chose it here.** 60 trials are enough to find good regions in a 9-dimensional space where grid search would be too coarse or too slow.

**Our result and what it means.** Best valA PR-AUC 0.208; parameter importance: tune_lgbm_importance.png.

**Likely questions.**
- *How is it different from random search?* It uses the results of earlier trials to choose the next.

## The p / d ordering rule (adjacent-swap proof)

**What it is.** Run tests in descending order of P(fail) / expected duration.

**How it works.** For adjacent independent tests i, j: running i first costs d_i + (1 − p_i) d_j of the time before the first failure in their stretch; j first costs d_j + (1 − p_j) d_i. i first is better iff p_i d_j > p_j d_i, i.e. p_i/d_i > p_j/d_j. Any order can be improved by such swaps until it is sorted by p/d (Smith's rule).

**Why we chose it here.** It turns a classifier's probability into the ordering that minimises expected time to the first failure.

**Our result and what it means.** MODELING.md compares p/d with p-only ordering (`lgbm_p`).

**Likely questions.**
- *Failures are not independent.* True (co-failures); the rule is optimal under independence and a strong heuristic otherwise; we measure the actual effect.

## APFDc

**What it is.** Average Percentage of Faults Detected, cost-cognizant: the area under 'share of faults found' vs 'share of test time spent'.

**How it works.** For each failing test at position i: cost_i = remaining suite time from i minus half of test i; APFDc = Σ cost_i / (n_faults × total time). 1 = all failures at the start, ≈ 0.5 random.

**Why we chose it here.** It is the LRTS paper's metric (so we can reproduce it) and it accounts for test cost.

**Our result and what it means.** Reproduction of the paper: GATE 2 True (BASELINES.md).

**Likely questions.**
- *Why also time-to-first-failure?* Developers wait for the first red test; TTFF is what they feel.

## PR-clustered bootstrap

**What it is.** Confidence intervals by resampling pull requests, not runs.

**How it works.** Each replicate draws PRs with replacement inside every project, recomputes project means, averages them.

**Why we chose it here.** Stages and rebuilds of one PR share code and flakiness; treating them as independent would give too-narrow intervals.

**Our result and what it means.** All CIs in BASELINES.md and MODELING.md.

**Likely questions.**
- *Why paired differences?* Comparing two methods on the same runs removes run difficulty from the variance.

## SHAP

**What it is.** Shapley-value feature attributions: how much each feature moved one prediction from the average.

**How it works.** TreeSHAP computes them exactly for tree ensembles; global importance = mean |SHAP|.

**Why we chose it here.** To check that the model relies on plausible signals and to explain rankings in smartci.

**Our result and what it means.** Agreement with LR coefficients (Spearman): 0.136.

**Likely questions.**
- *Is SHAP causal?* No: it explains the model, not the world.

## Chronological and rolling-origin evaluation

**What it is.** Train on the past, test on the future, never the reverse.

**How it works.** Builds are split 70/15/15 by start time per project; rolling-origin windows refit on everything before each 30-day window.

**Why we chose it here.** CI data drifts (Kafka's failure rate goes 0.60 → 0.97 across splits); random K-fold would leak the future.

**Our result and what it means.** Windows per project: {'activemq': 6, 'hadoop': 7, 'hbase': 6, 'hive': 10, 'jackrabbit-oak': 6, 'james': 6, 'kafka': 10, 'karaf': 19, 'log4j': 1, 'tvm': 5}.

**Likely questions.**
- *Why build-level, not run-level?* Stages of one build share a change; splitting them would leak.

## Bug mining (smartci learn)

**What it is.** Reintroducing a repository's own past bugs: take a fix commit with tests, put the source back to the parent, keep the fixed tests, run them.

**How it works.** Keep only commits whose touched tests pass on the fix and fail with the old source.

**Why we chose it here.** It produces real bugs with known revealing tests on the user's repo, without hand-picking.

**Our result and what it means.** REAL_WORLD.md.

**Likely questions.**
- *Isn't it biased?* Yes: towards test-backed fixes, and the revealing test usually came with the fix (regression catching). Stated in every report.

## Mutation testing (smartci mutate)

**What it is.** Small synthetic bugs (operator swaps, off-by-one, return None, negated conditions) at random covered lines.

**How it works.** Keep mutants that at least one existing test kills; the kill set is the 'failing tests'.

**Why we chose it here.** A benchmark of never-seen bugs, complementary to mined (known) bugs.

**Our result and what it means.** REAL_WORLD.md.

**Likely questions.**
- *Does it favour coverage-first?* Yes, because sites are drawn from covered lines; we say so.

## Simulation vs real runs (GATE 5)

**What it is.** Checking that the backtest's simulated time to first failure equals what real pytest does.

**How it works.** Draw 5 mined bugs and 5 mutants (logged seed), run real `pytest -x` in both orders, compare with the simulation within 10% plus measured start-up overhead.

**Why we chose it here.** Without it, the backtest could be an artefact of the simulator.

**Our result and what it means.** REAL_WORLD.md §simulation check.

**Likely questions.**
- *Why sequential, not side-by-side?* Two concurrent runs share the CPU and inflate both times.

## Why a simple baseline can win

**What it is.** On some repositories or subsets, a one-line rule (recently failed first, changed files first, coverage first) is as good as or better than the model.

**How it works.** Simple rules use exactly the strongest signal with no estimation noise; a model must learn that signal from other projects and can be miscalibrated for a new repo.

**Why we chose it here.** Honesty: smartci always reports the best simple baseline and recommends it when it wins.

**Our result and what it means.** BASELINES.md and REAL_WORLD.md list wins, ties and losses.

**Likely questions.**
- *Then why a model?* It combines weak signals (history, paths, co-failure, cost) where no single rule dominates, and degrades to the simple rule's behaviour when one signal dominates.
