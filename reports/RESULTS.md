# RESULTS: smartci: predicting CI test failures to run the right tests first

**The question.** When does machine learning beat simple rules for ordering tests, and when doesn't it?

**The answer.** Reordering tests helps enormously. ML gives a modest gain over simple rules on recurring failures, and loses to "fastest test first" on tests that fail for the first time.

Generated by `python -m stp.reports.results_md` from `reports/results/*.json`. Details: BASELINES.md (baselines and
the leak), FEATURES.md, MODELING.md (models, tuning, ablations, transfer), REAL_WORLD.md (smartci on real repos).

## 1. Problem

CI suites in the LRTS dataset (108,366 runs, 10 Apache projects) take hours. Running the tests most likely to fail
first surfaces a failure sooner without skipping anything. The hard case is **first-time failures**: tests that have
never failed, for which "run what failed recently" cannot help.

## 2. A leak-free setup, and a leak in the paper's baselines

Every feature is **as-of**: a run only sees results of runs that had *finished* when it started (end = start +
capped build duration). The LRTS paper's history baselines use the previous run *by start time*; in
49.8% of runs (macro) that run was still
running, and 45.8% of
"last outcome = fail" values come from unfinished runs. We reproduce the paper's numbers within ±0.005 (GATE 2:
PASS); re-running the *same* baselines as-of moves macro APFDc only slightly
(BASELINES.md §3): recent failures repeat, so losing the newest one rarely changes the ranking. The leak is real and
frequent, its effect on these baselines small. While reproducing we also found that the paper's published TVM
FirstFail numbers were computed with a different protocol than the other nine projects (WORKLOG, GATE 2).

## 3. Models

Binary classification of P(test class fails in this run) from 25 as-of features (history, cost, change relatedness,
co-failure memory), negative-sampled training, isotonic calibration on unsampled validation data, ordering by
P / expected duration. Logistic regression (elastic-net), random forest, LightGBM (Optuna), soft voting and stacking.

## 4. Error analysis: why the model loses where it loses

### 4.1 First-time failures of existing tests (model vs QTF)

**Hypothesis.** The model ranks tests that have failed before ahead of tests that never failed. When the failing test is one that never failed, the time spent on those earlier tests is wasted.

**Test.** All 222 held-out test-split runs with such a failure; tuned LightGBM vs QTF with the harness's tie-break seeds; per project the median over runs, then the mean over projects (`python -m stp.models.error_analysis`).

|  | LightGBM | QTF |
|---|---|---|
| Share of suite time spent before the first-time failure is reached | 16.4% | 9.1% |
| … of that time, spent on tests that had failed before | 74.1% | 26.7% |
| Position of that failure in the order (0 = first, 1 = last) | 0.46 | 0.61 |

Tests that had failed before are 33% of a run's tests (median). The model gives passing tests that failed before a mean P(fail) of 0.0056, against 0.0006 for never-failed tests (9×). The first-time-failing test itself sits at the 74% duration percentile of its run (a long test), and dividing by duration pushes it back further.

**Verdict: supported.** The model reaches the first-time failure later, and most of the time before it goes to previously-failed tests, far more than their share of the suite. QTF ignores history and does not pay that cost. It is the price of the gain on recurring failures, not a bug.

### 4.2 Why the TVM-only model collapses from validation to test

**Observation.** TVM-only PR-AUC is 0.680 on validation (valB) and 0.037 on test. **Hypothesis:** drift between the two periods.

**Test.** For TVM, per split (valA / valB = time halves of the validation runs): failure rates, how concentrated failures are, how many come from test classes seen or failing in train, and the population stability index (PSI) of the main features against train.

| TVM | train | valA | valB | test |
|---|---|---|---|---|
| Runs | 29,465 | 2,824 | 2,824 | 5,378 |
| Failed-run rate | 14.4% | 5.7% | 11.8% | 5.2% |
| Row failure rate | 0.183% | 0.405% | 0.417% | 0.134% |
| Failures per failing test class | 22.3 | 7.5 | 13.3 | 5.7 |
| Rows whose test class never appeared in train | 0.0% | 0.3% | 63.7% | 68.6% |
| Failures from classes never seen in train | 0.0% | 0.5% | 68.7% | 79.5% |
| Failures from classes that already failed in train | 100.0% | 79.3% | 25.7% | 16.1% |

PSI against train (largest on test first; < 0.1 small, > 0.25 large):

| Feature | valA | valB | test |
|---|---|---|---|
| `h_n_runs_seen` | 0.93 | 1.97 | 1.22 |
| `h_fail_rate` | 0.54 | 1.00 | 0.51 |
| `h_n_fail` | 0.04 | 0.20 | 0.22 |
| `h_days_since_last_fail` | 0.12 | 0.30 | 0.14 |
| `chg_n_files` | 0.38 | 0.23 | 0.10 |
| `h_fails_last_30d` | 0.14 | 0.14 | 0.04 |

**What the data shows.** The row failure rate is 3.1× lower in test (0.134% vs 0.417% in valB); PR-AUC falls with the base rate even when the ranking is equally good; validation failures repeat: each failing class fails 13.3 times on average in valB but 5.7 times in test, so history features (which see earlier validation runs as-of) catch far more of valB's failures; fewer test failures come from classes that already failed in train (16% vs 26%). **What it rules out.** feature drift against train is large in *both* valB and test (`h_n_runs_seen`, `h_fail_rate`), so it cannot explain why valB is good and test is bad; the share of rows from classes unseen in train is similar (64% valB, 69% test): most TVM test classes in both periods are new (added, renamed or moved since train), which hurts both periods alike.

**Verdict.** Partly supported, but not as feature drift: the validation period was easy (frequent, repeating failures that history catches), and the test period has rarer, more varied failures. One project and one validation period are too little to choose a model on; pooling all 10 projects (the shipped `all_to_tvm`) is more robust on test.

### 4.3 Can the trade-off be tuned? A probability floor

**Idea.** Order by max(P, f) ÷ duration. With f = 0 this is the model; as f grows every test gets the same probability and the order becomes "fastest first". A small f stops the model from pushing never-failed tests to the very end.

**Rule, fixed before the test split was scored.** , fixed before the test split is scored (also written to the JSON before the test step runs):
  on the VALIDATION split, among the f whose macro APFDc on All failed runs is at most 0.005 below f = 0, take the f
  with the highest macro APFDc on FirstFail-old; if none beats f = 0 on FirstFail-old, f* = 0.
Ship rule: smartci gets the floor only if f* > 0 and, on the TEST split (reported once), the paired difference
  f* − 0 on FirstFail-old has a 95% PR-clustered CI above 0 and the All mean difference is ≥ −0.005.

Validation curve (macro APFDc, tuned LightGBM):

|---|---|---|
| f=0 | 0.873 | 0.697 |
| f=1e-05 | 0.873 | 0.701 |
| f=3e-05 | 0.873 | 0.703 |
| f=0.0001 | 0.873 | 0.709 |
| f=0.0003 | 0.872 | 0.726 |
| f=0.001 | 0.864 | 0.754 |
| f=0.003 | 0.845 | 0.778 |
| f=0.01 | 0.800 | 0.806 |

**Test split, reported once (f* = 0.0003).** Δ vs f = 0: all failures -0.004 [-0.006, -0.002], first-time failures of existing tests +0.050 [+0.024, +0.085]. With the floor the model scores 0.758 there against QTF's 0.800: it closes part of the gap but still loses to QTF. **Shipped in smartci** (`ordering_floor` in the model's schema.json).


## 5. Real repositories (smartci)

- **networkx**: 68 reproducible mined bugs, 300 mutants; best simple baseline (all bugs): changed_files_first; smartci does not clearly beat 'changed_files_first' here; use changed_files_first (or keep smartci only if its median is lower and you accept the uncertainty)

See REAL_WORLD.md for the tables, win/tie/loss, every loss, the simulation-vs-real check (GATE 5) and caveats.

## 6. Limitations

- LRTS has test-class granularity, no execution order and summed (not wall-clock) test time; wall-clock numbers are
  approximate (× median build/suite ratio, capped at 1).
- Models are evaluated at one origin (the test split); baselines also on every rolling-origin window.
- Small projects have < 30 test runs each; only their pooled macro is interpreted.
- Real-repo bugs are reintroduced known bugs or synthetic mutants (REAL_WORLD.md caveats).
- A simple rule can win; smartci reports it and recommends it when it does.
